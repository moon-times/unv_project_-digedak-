# 👥 딕으닥 — 역할 분담안 (3인)

> 기능 흐름을 기준으로 **입력 · 타임라인(A) → 음악 엔진(B) → 앱 · 서버 · 저장(C)**으로 나눴습니다.
> 세 역할이 `SongState`라는 하나의 데이터를 중심으로 연결되므로, 타입만 먼저 합의하면 각자 독립적으로 개발할 수 있습니다.
> 설계 기준: 하이브리드 분석(규칙 엔진이 주연, LLM은 설명 · 재추천 보조), 스튜디오는 고정 타임라인 + 단계별 도구 패널.

---

## 역할 요약

| 역할 | 한 줄 요약 | 주요 기술 | 담당 폴더 | 추천 성향 |
|---|---|---|---|---|
| **A. 입력 · 타임라인** | 허밍을 음표로 바꾸고, 곡 전체를 보여 주고 고치는 화면 | Web Audio API, Pitchy, Canvas/SVG | `features/recorder`, `features/piano-roll`(타임라인) | 인터랙티브 UI, 신호 처리에 관심 |
| **B. 음악 엔진** | 음표에 코드와 반주를 붙이고 소리를 냄 | 분석 엔진(규칙 기반), Tone.js, smplr | `lib/music`, `features/arranger`, `features/player`, `features/mixer` | 음악 이론 지식, 로직 설계 선호 |
| **C. 앱 · 서버 · 저장** | 화면 틀, 계정, 저장, 내보내기, 배포 | Next.js, Supabase, Zustand, LLM API, Zod, Vercel | `app/`(페이지 · `api`), `store`, `lib/supabase`, `lib/schemas.ts`, `types`, `features/editor` | 백엔드 · DevOps, 전체 구조 관리 선호 |

> 음악 이론을 아는 팀원이 있다면 **B**를 맡기는 것을 추천합니다. 분석과 반주의 품질이 결과물 인상을 가장 크게 좌우합니다.

---

## A. 입력 · 타임라인 담당

### 책임 범위
- 녹음 패널: 마이크 권한 요청, BPM · 카운트인 메트로놈, 최대 30초 녹음, 실시간 음 이름 표시, 무음 · 권한 거부 안내
- 피치 검출(Pitchy) → 음표로 묶기(같은 음 연결, 짧은 잡음 제거) → 퀀타이즈(16분음표 · 반음 단위)
- **고정 타임라인 컴포넌트**: 피아노롤 편집(추가 · 삭제 · 드래그 이동 · 길이 조절 · 스냅), 코드 레인 표시, 반주 3줄(드럼 · 베이스 · 건반) 보기 전용 표시, 재생 위치 표시
- 보정 · AI 분석 패널의 화면: 분석 카드(키 · 추천 장르 · BPM), "왜 이 코드인지" 설명 표시 (계산은 B)
- (선택) 원본 파형 · 구간 자르기(wavesurfer.js), 오선보(VexFlow), 코드 블록 직접 수정

### 산출물
- `recordAndDetect(): Promise<{ notes: Note[]; blob: Blob }>`
- `quantize(notes, bpm, grid): Note[]`
- `<Timeline />` 컴포넌트 (store의 `melody` · `chords` · 반주를 읽고, `melody` · `chords`를 수정)

### 협업 포인트
- **→ B**: B가 내보내는 재생 위치를 받아 타임라인에 표시
- **→ C**: 녹음 `Blob`을 넘겨 Storage 업로드, 녹음 · 분석 패널을 C의 스튜디오 틀 패널 칸에 배치

---

## B. 음악 엔진 담당

### 책임 범위
- 음악 이론 유틸 (코드 → 구성음, 스케일, 전위)
- **규칙 엔진 분석**: 키 판별(Krumhansl–Schmuckler), 코드 진행 배정(Viterbi), 스타일 규칙, 기본 설명 문장 틀
- **반주 템플릿 엔진**: 팝 · 발라드 · 록의 드럼 · 베이스 · 건반 패턴, 장르를 바꾸면 반주 즉시 재생성
- Tone.js 재생 엔진, smplr 악기 로딩, 트랙별 채널(볼륨 · 뮤트 · 솔로)
- 반주 패널(장르 카드) · 믹서 패널: 자기 엔진을 직접 조작하는 화면이므로 함께 담당
- (선택) 섹션 구성(인트로 · 코러스), 트랙 이펙트(리버브 · EQ), LLM 재추천 코드의 규칙 엔진 점수 검사

### 산출물
- `analyzeSong(melody, bpm): { key, chords, recommendedStyle, bpmSuggestion, explanation }` — 브라우저 규칙 엔진 (기본 분석)
- `generateAccompaniment(chords, style, bpm): { drums: Note[]; bass: Note[]; keys: Note[] }`
- `player.play() / stop() / seek() / setBpm()`, 재생 위치 구독, 트랙별 Tone 채널
- 오프라인 렌더링에 재사용할 예약 함수 (C가 WAV를 만들 때 사용)

### 협업 포인트
- **→ A**: 재생 위치 공유, 분석 결과는 store를 거쳐 A의 코드 레인 · 분석 카드에 표시
- **→ C**: WAV 렌더링용 예약 함수 제공, LLM 재추천 코드는 점수 검사 후에만 반영

---

## C. 앱 · 서버 · 저장 담당

### 책임 범위
- 저장소 · 개발 환경 · 환경변수 · Vercel 배포
- **페이지와 화면 틀**: 랜딩, 인증(이메일 · GitHub · Google), 내 프로젝트, 스튜디오 틀(제목 · 자동 저장 표시 · 진행 바 · 패널 전환 · 하단 재생 바), 내보내기 팝업창(회원 / 게스트)
- Supabase Auth, `projects` 테이블, RLS, Storage(녹음 원본)
- 게스트 작업 이어 가기: 로그인하면 게스트로 작업하던 곡을 저장하고 스튜디오로 복귀
- Zustand `songStore` 설계와 유지 (**SongState 타입의 관리자**), 저장 · 불러오기 · 자동 저장
- **`/api/analyze` (LLM 보조)**: 설명 다듬기 프롬프트, Zod 응답 검증, 재시도, 실패 시 규칙 엔진 결과 유지, 사용자별 호출 한도, API 키 보호
- WAV 오프라인 렌더링 → 다운로드
- 공통 디자인: 색, 버튼 · 카드 등 공통 컴포넌트, 마스코트 상태(빈 화면 · 로딩)
- (선택) AI 재추천의 LLM 요청 쪽, 공유 링크 · 공유 페이지, WAV 서버 저장

### 산출물
- `songStore` (상태 + 액션: `setMelody`, `setChords`, `setAccompaniment`, `updateTrack` 등)
- `saveProject() / loadProject()`
- `POST /api/analyze` — 입력: `{ melody, analysis, request? }` / 출력: 같은 형식에서 `explanation`(다듬은 설명) 또는 `chords`(재추천)만 채워 반환
- `exportWav(song): Promise<Blob>`

### 협업 포인트
- **→ A, B**: store 액션 제공, 타입 변경 시 공지
- **→ B**: WAV 렌더링에 쓸 예약 함수 인터페이스 합의, 재추천 코드를 B의 점수 검사에 넘김

---

## 서로 맞물리는 지점

| 연결 | 내용 |
|---|---|
| A ↔ B | B가 재생 위치를 내보내고 A의 타임라인이 표시. 분석 결과(`chords` 등)는 store를 거쳐 A의 코드 레인에 표시 |
| A ↔ C | A의 녹음 `Blob`을 C가 Storage에 업로드. A의 패널은 C가 만든 스튜디오 틀의 패널 칸에 들어감 |
| B ↔ C | C의 내보내기가 B의 예약 함수로 WAV 생성. LLM 재추천 코드는 C가 받아 오고 B의 점수 검사를 통과해야 반영 |
| 전원 ↔ C | `SongState` 타입은 C가 관리하고, 변경 시 전원 합의 |

---

## 공동 책임

| 항목 | 주 담당 | 비고 |
|---|---|---|
| SongState 타입 설계 | C (주도) + 전원 | 개발 시작 전에 확정, 변경 시 전원 합의 |
| UI 디자인 통일 | C (주도) + 전원 | 공통 컴포넌트를 함께 사용 |
| 통합 테스트 | 전원 | 역할을 바꿔 서로의 기능을 교차 테스트 |
| README · 문서 | C (주도) | 각자 담당 기능 섹션 작성 |

---

## 업무량 균형

- **A**: 타임라인 컴포넌트가 이 프로젝트에서 가장 손이 많이 가는 UI입니다. 대신 서버 쪽 일은 없습니다.
- **B**: LLM 서버 부분을 C로 넘겨 음악 로직(분석 · 반주 · 재생)에 집중합니다. 키 판별은 음표 배열만 받는 독립 함수라서, 밀리면 피치 검출 결과를 다루는 A가 맡기 쉽습니다.
- **C**: 할 일의 종류가 가장 많지만 대부분 정해진 방식을 따르는 작업입니다(인증, DB, 페이지, 배포). 밀리면 공통 디자인을 A와 나눠 맡습니다.
- 한 명이 빠지는 상황에 대비해, 각자 **자기 기능을 다른 팀원에게 정기적으로 짧게 설명**해 두는 것을 추천합니다.

## 협업 규칙

### 브랜치 전략
- `main` — 항상 배포 가능한 상태, 직접 push 금지
- `feat/{기능명}` — 기능 개발 (예: `feat/timeline`)
- `fix/{내용}` — 버그 수정
- PR은 **최소 1명 리뷰** 후 병합, Vercel 미리보기 URL로 동작 확인

### 커밋 메시지
```
feat: 피아노롤 음표 드래그 이동 추가
fix: 무음 녹음 시 빈 배열 처리
refactor: 코드 구성음 변환 함수 분리
docs: README 실행 방법 추가
```

### 인터페이스 변경 규칙
- `types/song.ts`, `lib/schemas.ts`를 수정할 때는 **PR 설명에 변경 사항을 명시**하고 팀원 전체를 리뷰어로 지정합니다.
- 다른 담당자의 폴더를 수정해야 하면 먼저 해당 담당자에게 알립니다.

### 커뮤니케이션
- 정기 회의: 계획 공유 / 데모 공유
- 막힌 작업은 **3일 이내에 공유**
- 이슈와 진행 상황은 GitHub Projects 칸반으로 관리
